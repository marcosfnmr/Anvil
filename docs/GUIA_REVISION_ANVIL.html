1. Resumen ejecutivo

Anvil permite diseñar escenarios OT mediante un mapa, ejecutar runtimes aislados en contenedores y observar o accionar señales mediante protocolos industriales. Separa los dispositivos de control (PLC, HMI, SCADA y estaciones) de los objetos del proceso (bombas, depósitos, válvulas y sensores). Las relaciones físicas y las señales de control son distintas: una tubería transporta caudal; un cable lógico lleva una señal a un PLC.

3. Arquitectura a alto nivel

  1. Interfaz web: editor de escenarios, mapa de dispositivos y objetos, inspectores, HMI, SCADA, telemetría, actividades y controles de operación.
  2. API/backend: FastAPI valida modelos, persiste escenarios y revisiones en SQLite, aplica acceso y auditoría, produce mapas de E/S, diagnósticos y operaciones de runtime.
  3. Docker manager: convierte el escenario en runtimes, redes y proxies. Las redes de laboratorio y dispositivos se crean bajo demanda y se asocian a identificadores de escenario/nodo.
  4. Gate de Docker: el backend llega al socket Docker a través de un proxy limitado a operaciones e imágenes permitidas por Anvil.
  5. Runtimes: el PLC S7 ejecuta ciclo y lógica básica; Modbus TCP/RTU atiende mapas de registros; un runtime de campo mantiene objetos y enlaces de señal; SCADA/HMI leen y escriben señales autorizadas.

El diseño separa la definición persistente del escenario del estado vivo de los contenedores. Esto permite detener, consultar salud, reconciliar faltantes y exportar un bundle de despliegue sin confundir configuración con telemetría.

4. Cómo se modela una fábrica

Un escenario guarda dispositivos, zonas, objetos independientes de campo, enlaces, reglas y posiciones del mapa. Una bomba puede estar conectada físicamente a una válvula y un tanque, y además recibir una señal digital de salida de un PLC. Esos son dos grafos relacionados pero diferentes:

  • Proceso físico dirigido: origen hidráulico → tuberías/válvulas/distribuidores → entrada de tanque o descarga terminal. Transporta caudal y permite estimar nivel/presión con el modelo disponible.
  • Señales: salida PLC → entrada de mando del actuador; sensor → entrada analógica/digital de PLC. Tiene tipo, dirección, calidad y política de escritura.
  • Red OT: conectividad de nodos, zona Purdue y rutas de protocolo declaradas. Una línea visual no implica routing IP genérico.
  • Control entre PLC: vínculos S7 declarados entre emisor y receptor, sondeados desde el nodo correspondiente.

Los enlaces se dibujan con estilos distintos. El mapa persiste coordenadas y conexiones; la navegación permite ajustar el viewport sin cambiar posiciones guardadas. El objeto de campo puede crearse y configurarse sin entrar en el inspector del PLC.

5. PLC y protocolos que sí existen

S7

El runtime ofrece un servidor S7 accesible con clientes Snap7, memoria DB/marcas/entradas/salidas y canales BOOL/REAL. Las áreas I son de solo lectura para operadores; salidas Q/M y DB requieren permisos configurados. Los bloques disponibles incluyen ON/OFF con histéresis, lógica booleana y TON básico. Existen enlaces S7 entre PLC y opciones de fallos/temporización representativas.

Modbus

El dispositivo Modbus TCP configura unit ID, puerto interno, mapa de coils, discrete inputs, holding e input registers; el cliente puede leer/escribir las funciones admitidas. RTU se representa mediante tramas Modbus sobre un túnel TCP y pseudo-terminal, no mediante un bus eléctrico RS-485.

HMI y SCADA

HMI y SCADA leen puntos configurados, muestran calidad, tendencias/alarma disponibles y permiten escrituras limitadas por rol, mapa de E/S y auditoría. La HMI puede mostrar el sinóptico del proceso, pero solo asocia valores de tags realmente leídos desde destinos configurados; un objeto visual sin tag no debe confundirse con telemetría.

Anvil es un simulador de entrenamiento e integración de software. No es un clon completo de Siemens ni reemplaza comportamiento eléctrico, firmware, tiempos garantizados o validación sobre hardware certificado.

6. API e interfaz: qué debe corresponder

La interfaz presenta solo las operaciones que respaldan rutas reales: guardar y cargar escenario, catálogo, estado, mapa de E/S, diagnósticos, lectura/operación HMI y control de runtime. Una vista o indicador no se considera implementado solo porque exista visualmente; tiene que consultar una ruta que lea el dispositivo y aplicar los permisos de escritura del backend.

El editor trabaja con modelos validados y la API serializa errores de esquema con sus ubicaciones. La página de diagnósticos consulta el backend antes de desplegar y pide confirmación para continuar con advertencias. Los errores bloqueantes de esquema se presentan como errores, no como aviso inocuo.

La matriz de trazabilidad señala por separado qué interacciones tienen prueba de API, prueba unitaria, smoke Docker o automatización de navegador. El estado “Parcial” conserva las limitaciones explícitas aunque la parte principal funcione.

7. Avance actual: diagnósticos de proceso RF-04

Antes, el preflight podía detectar objetos de campo aislados y puertos que faltaban en depósitos, distribuidores o colectores. No detectaba dos ramas que, individualmente, sí tenían conexiones pero no formaban un circuito continuo.

Qué comprueba ahora

  • Construye un grafo dirigido usando objetos hidráulicos soportados: bomba, variador, tanque, tubería, válvula, válvula proporcional, distribuidor y colector.
  • Busca caminos desde bombas/variadores y tanques con salida hasta depósitos con entrada. También permite válvulas terminales conectadas como descarga, para no marcar como error los vaciados válidos del escenario demo.
  • Excluye conexiones cuyo destino es el puerto de medición: un sensor de nivel no constituye una tubería hidráulica.
  • Si una rama vinculada queda fuera de cualquier camino continuo, crea el aviso field_process_path_incomplete con un mensaje que propone conectar sus ramas hasta una fuente y un destino.
  • El aviso es consultivo. Guardar sigue permitido y el endpoint puede responder valid: true mientras no existan errores de validación del modelo.

Por qué esto no es un solver de fluidos

La comprobación verifica conectividad y dirección declaradas, no diámetros, presión de red, conservación global ni convergencia de lazos. Es un diagnóstico de topología que ayuda a localizar ramas huérfanas. Las limitaciones del balance de caudal se mantienen en RF-20/21.

Pruebas API: topología fragmentada (aviso, pero escenario válido), topología fuente→válvula→tanque sin aviso y colector/distribuidor completo. 8. Seguridad y aislamiento: alcance de las afirmaciones

Anvil incluye autenticación basada en rol, separación por escenarios, auditoría, políticas de E/S, redes Docker internas por zona, límites de recursos y un proxy de Docker. El acceso desde el host a protocolos está cerrado por defecto y se habilita de forma explícita en el escenario. La estación de participante y los servicios auxiliares tienen restricciones adicionales.

Esto reduce exposición accidental en un laboratorio local, pero no constituye certificación, hardening universal ni seguridad equivalente a una planta. Docker, kernel, credenciales, host, segmentación física y configuración de red siguen bajo responsabilidad del entorno de ejecución. Los requisitos RFN tienen su propia evidencia y lagunas descritas en la matriz.

10. Qué significa “probado”

  • Unitario: valida una función o componente aislado.
  • API: usa FastAPI TestClient y base efímera; confirma contratos, permisos y persistencia en ese límite.
  • Integración Docker: levanta runtimes y clientes para comprobar protocolo o interacción real entre servicios.
  • Navegador: automatiza acciones visibles sobre un backend configurado; no reemplaza auditoría manual de accesibilidad.
  • Benchmark: informa tamaño del escenario, host, imágenes, tiempos y límites. No extrapola linealmente a una VM distinta.

11. Cómo abrir esta guía y qué se ha desplegado

El preview de esta guía es un servidor estático en http://localhost:8007/GUIA_REVISION_ANVIL.html, limitado a loopback. Sirve el directorio docs/ y no tiene conexión con la API ni con Docker. No cambia el stack de Anvil.

python3 -m http.server 8007 --bind 127.0.0.1 --directory docs

Desde Windows/Brave puedes abrir el mismo http://localhost:8007/GUIA_REVISION_ANVIL.html. El servidor se mantiene como proceso local de esta sesión; si se reinicia la máquina, vuelve a iniciarlo con el comando anterior. Para cerrar solo ese servidor, identifica su proceso por el comando de http.server y termina ese proceso específico; no detengas procesos de Anvil.

Los previews de producto observados en 8003 y 8005 responden HTTP 200 y no fueron modificados. El 8006 ya estaba ocupado por otra instancia y también se preservó.

12. Limitaciones conocidas y próximos pasos razonables

  • La simulación de PLC representa servicios de protocolo y lógica acotada; no reproduce firmware completo, ciclo de scan certificado, catálogo TIA, hardware, redundancia o diagnóstico de fabricante.
  • El modelo hidráulico es determinista y representativo. No resuelve redes nodales generales, transitorios ni curva real de bomba/VFD.
  • Modbus RTU corre sobre túnel/software; no emula el medio eléctrico RS-485.
  • Algunos enlaces Ethernet son descriptivos; el switch lógico no emula VLAN/STP ni convierte el escenario en routing IP general.
  • Protocolos como OPC UA, DNP3, IEC-104, EtherNet/IP, Profinet e IEC 61850 siguen pendientes según la matriz.
  • Una muestra mixta de 30 nodos pasó en 11,416 s con 15 CPU-quota configuradas sobre un host de 12 CPU. Las cuotas son topes, no reservas; no se midió carga de proceso concurrente ni se extrapoló a otros hosts.
  • La advertencia de camino hidráulico detecta conectividad dirigida; futuras iteraciones podrían incorporar puertos y criterios por clase, ciclos/retornos y cobertura visual directa del diálogo de preflight.
