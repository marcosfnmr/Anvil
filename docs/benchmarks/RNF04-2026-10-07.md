# RNF-04: medición local de 20 PLC S7

Fecha: 2026-10-07. Resultado válido solo para el host y el perfil descritos.

## Método

[`integration/capacity_benchmark.py`](../../integration/capacity_benchmark.py)
creó tres escenarios independientes mediante una API local temporal con base
SQLite separada. Cada escenario tenía 20 PLC S7 con una válvula BOOL y un sensor
REAL, en una red Docker interna. Cada contenedor usó la misma imagen y el
healthcheck de la imagen comprobó el puerto TCP/102. El script midió la duración
informada por Anvil y el tiempo observado por el cliente, comprobó que los 20
nodos llegaron a `running` y detuvo/eliminó cada escenario.

## Resultado

| Muestra | Duración informada por Anvil | Tiempo del cliente |
|---:|---:|---:|
| 1 | 8,555 s | 8,607 s |
| 2 | 8,669 s | 8,696 s |
| 3 | 8,607 s | 8,626 s |

Mediana: **8,607 s**. Máximo observado: **8,669 s**. Las tres ejecuciones
quedaron bajo el umbral orientativo de 300 s usado en el benchmark. El endpoint
mide desde la entrada en `DockerManager.deploy` hasta la inspección de todos los
contenedores después del arranque; para este perfil el healthcheck TCP/102 confirmó
que el servidor S7 escuchaba.

## Host y límites

- WSL2 Linux x86_64, kernel `6.6.87.2-microsoft-standard-WSL2`.
- Docker Engine `29.8.1`, 12 CPUs visibles y 8 146 599 936 bytes de memoria
  visibles para Docker.
- Python del backend/benchmark: 3.13.5.
- Imagen de PLC: `anvil/plc-s7:s7-peer-route-test`, ID
  `sha256:0bb828fb239bc1170956edc9de0e78ac265f9e80cc12365520bc022b4a5e4072`.
- Los 20 PLCs ejecutaron el servidor S7 y el scan normal con puntos configurados.
  No se generó tráfico de cliente concurrente ni carga de control de proceso.
- No se midieron Modbus, HMI/SCADA, motor de campo, carga concurrente, navegador
  con 100 nodos, múltiples hosts ni imágenes frías.
- Los previews `8003` y `8005` permanecieron activos. La verificación posterior
  no encontró contenedores ni redes con las etiquetas de los escenarios del
  benchmark. El backend temporal escuchó solo en `127.0.0.1:8014` y se detuvo.

El resultado demuestra que 20 PLC S7 de este perfil se desplegaron dentro del
objetivo orientativo en este host. No garantiza ese tiempo en otros equipos ni en
topologías OT mixtas; RNF-04 sigue parcial hasta caracterizar esos perfiles.

## Perfil mixto S7 y Modbus TCP

El 7 de octubre de 2026 se ejecutó una muestra adicional con el perfil `mixed`
del mismo benchmark: 20 dispositivos en una red interna, 10 PLC S7 con válvula
BOOL y sensor REAL y 10 servidores Modbus TCP con coil, holding register e input
register. Anvil esperó al healthcheck de cada imagen y confirmó los 20 nodos en
`running`. El backend temporal usó una base SQLite nueva, bootstrap de cuenta
efímera y las imágenes locales; no se usó ni modificó la base de los previews.

| Muestra | Duración informada por Anvil | Tiempo del cliente |
|---:|---:|---:|
| 1 | 8,026 s | 8,045 s |

La muestra quedó bajo el mismo objetivo orientativo de 300 s. Es una sola
ejecución y no permite calcular variabilidad ni comparar hosts; RNF-04 permanece
parcial. Los previews `8003` y `8005` permanecieron activos. El escenario fue
detenido y eliminado por el script al terminar, y el backend temporal se cerró.

Repetición, con el backend aislado en `127.0.0.1:8014`, imágenes disponibles y
autenticación temporal entregada por `ANVIL_BENCHMARK_TOKEN`:

```bash
PYTHONPATH=backend .venv/bin/python integration/capacity_benchmark.py \
  --base-url http://127.0.0.1:8014 --profile mixed --nodes 20 --samples 3
```

Para más de 30 nodos el benchmark exige `--allow-large-run` y las identidades de
un daemon Docker y backend aislados: versión exacta del Engine, huella SHA-256
del nombre del daemon e identidad de `GET /api/health`. El backend de prueba
debe tener `ANVIL_INSTANCE_ID` único configurado. Antes de crear escenarios el
script compara estas identidades y aborta ante cualquier diferencia. En las
ejecuciones históricas de hasta 30 nodos los argumentos de identidad son
optativos. No uses las identidades de los previews compartidos. El perfil de 100
nodos no se ha ejecutado en el daemon compartido.

Ejemplo una vez que el operador ya ha comprobado un daemon de prueba dedicado:

```bash
PYTHONPATH=backend .venv/bin/python integration/capacity_benchmark.py \
  --base-url http://127.0.0.1:8014 --profile mixed --nodes 100 --samples 1 \
  --allow-large-run \
  --expected-docker-server-version "$EXPECTED_TEST_DOCKER_VERSION" \
  --expected-docker-name-sha256 "$EXPECTED_TEST_DOCKER_NAME_SHA256" \
  --expected-api-health '{"status":"ok","instance_id":"capacity-test-unique"}'
```

`EXPECTED_TEST_DOCKER_NAME_SHA256` se calcula fuera del repositorio como
`sha256sum` del nombre devuelto por `docker info --format '{{.Name}}'` en el
daemon dedicado. Configura `ANVIL_INSTANCE_ID=capacity-test-unique` solo en el
backend efímero. Un healthcheck común `{"status":"ok"}` no identifica por sí
solo una instancia y no basta para un run superior a 30 nodos. No se deben
copiar tokens ni credenciales al repositorio o al informe.

## Ampliación mixta a 22 nodos — 2026-10-08

Se ejecutó una muestra del perfil `mixed` con 22 dispositivos (11 PLC S7 y 11
Modbus TCP), sobre Docker Engine local, API temporal sin autenticación en
`127.0.0.1:8015` y SQLite separada. Los clientes S7/Modbus no generaron carga
adicional; el benchmark esperó los healthchecks de las 22 imágenes.

| Muestra | Nodos | Duración informada por Anvil | Tiempo del cliente |
|---:|---:|---:|---:|
| 1 | 22 (11 S7 + 11 Modbus) | 9,253 s | 10,406 s |

El objetivo orientativo fue 300 s. Este resultado es una sola muestra y no
caracteriza variabilidad. El host fue WSL2 x86_64, Docker Engine 29.8.1, 12 CPU
y 8 146 598 144 bytes de memoria visibles para Docker. Se usaron las imágenes
locales `anvil/plc-s7:s7-peer-route-test` (`sha256:0bb828fb239bc1170956edc9de0e78ac265f9e80cc12365520bc022b4a5e4072`) y
`anvil/modbus-tcp:dev` (`sha256:02eee76070733f92cca7dbbc9c3b3d532905701f28af7e830939a9d68ee24c53`).
El escenario y su red se detuvieron y eliminaron; no quedaron contenedores con
label de escenario del benchmark. Los previews 8003 y 8005 siguieron activos.

También se intentó una muestra mixta de 30 nodos. La API la rechazó con HTTP 409
antes de crear contenedores: los 15 000 000 000 nanocpus que reservaban sus
contenedores exceden el presupuesto configurado de 12 000 000 000 nanocpus. El
script detuvo y eliminó ese escenario vacío. No se elevó el presupuesto para
forzar la muestra, ya que excedería los 12 CPU disponibles en este host.

## Repetición

Con una API temporal aislada, SQLite independiente y la imagen PLC disponible:

```bash
PYTHONPATH=backend ANVIL_PLC_IMAGE=anvil/plc-s7:s7-peer-route-test \
  .venv/bin/python integration/capacity_benchmark.py \
  --base-url http://127.0.0.1:8014 --profile plc-s7 --nodes 20 --samples 3
```

Usa `--profile gateway` para comparar la orquestación de nodos auxiliares
ligeros o `--profile modbus-tcp` para solo Modbus. El script selecciona subredes
/24 de su pool que Docker no tenga ocupadas. Los resultados anteriores de PLC S7
se pueden reproducir como se indica arriba con `--profile plc-s7`.

## Perfil mixto a 30 nodos y presupuesto CPU-quota — 2026-10-08

Se midió una muestra mixta de 30 nodos: 15 PLC S7 y 15 servidores Modbus TCP.
Se usó una API efímera en `127.0.0.1:8016`, con SQLite nueva, autenticación
desactivada y sin limpieza de recursos Docker ajenos. La primera ejecución llegó
a validar imagen y cuota, pero se rechazó porque la API apuntaba a la etiqueta
S7 `anvil/plc-s7:dev`, inexistente en este host; el escenario vacío se eliminó.
Al configurar ambas imágenes locales correctas, el despliegue se completó:

| Muestra | Presupuesto | Nodos | Duración Anvil | Tiempo cliente |
|---:|---|---:|---:|---:|
| 1 | 15 CPU-quota explícitas | 30 (15 S7 + 15 Modbus) | 11,416 s | 14,731 s |
| 2 | Predeterminado 15 CPU-quota | 30 (15 S7 + 15 Modbus) | 11,451 s | 13,185 s |

El host fue WSL2 x86_64, Docker Engine 29.8.1, 12 CPU y 8 146 591 744 bytes
de memoria visibles. Las imágenes eran S7 `anvil/plc-s7:s7-peer-route-test`
(`sha256:0bb828fb239bc1170956edc9de0e78ac265f9e80cc12365520bc022b4a5e4072`)
y Modbus `anvil/modbus-tcp:dev`
(`sha256:02eee76070733f92cca7dbbc9c3b3d532905701f28af7e830939a9d68ee24c53`).
El presupuesto de la API de benchmark era 15 000 000 000 nano-CPU para permitir
la suma de los límites máximos de los 30 contenedores; cada PLC/Modbus mantuvo
su límite individual original de 500 000 000 nano-CPU. Los 15 CPU-quota sumados
no son 15 CPUs reservadas: el host expone 12 CPUs y Docker reparte el tiempo
físico. No se generó tráfico de clientes concurrentes ni se capturó un perfil de
CPU/memoria durante el despliegue, por lo que no se concluye que un scan cargado
mantenga su periodo nominal.

La segunda muestra confirmó el despliegue usando el nuevo valor predeterminado
sin override: la API registró `15000000000` nano-CPU al arrancar. El valor de
`ANVIL_SCENARIO_MAX_NANO_CPUS` pasó de
12 000 000 000 a 15 000 000 000. Es un techo por escenario para permitir este
perfil y conserva los límites Docker por contenedor; no coordina varios
escenarios y puede permitir competencia de CPU bajo carga. Los operadores deben
ajustarlo al host y al perfil previsto. Se añadió un test unitario que garantiza
que 30 nodos mixtos caben en el presupuesto predeterminado.

Repetición con Docker, imágenes disponibles y una API temporal configurada con
las mismas etiquetas. Para validar el presupuesto nuevo, omite la variable
`ANVIL_SCENARIO_MAX_NANO_CPUS` y usa la configuración predeterminada:

```bash
PYTHONPATH=backend ANVIL_PLC_IMAGE=anvil/plc-s7:s7-peer-route-test \
  ANVIL_MODBUS_IMAGE=anvil/modbus-tcp:dev \
  .venv/bin/python integration/capacity_benchmark.py \
  --base-url http://127.0.0.1:8016 --profile mixed --nodes 30 --samples 1
```

El benchmark limpió cada escenario y su red al finalizar. Los previews 8003 y
8005 se conservaron; las API temporales se cerraron. Las dos muestras son
consistentes en este host, pero no demuestran disponibilidad garantizada ni
throughput sostenido.
